## 3. 服务端修复

服务端独立仓库位于：`C:\Code\React\mde-server`。

### 3.1 注册接口 HTTP 500

生产日志中的真实异常：

```text
Updating the path 'refreshTokens' would create a conflict at 'refreshTokens'
```

原实现对 MongoDB 的同一个 `refreshTokens` 字段在一次更新中同时执行 `$pull` 和 `$push`。MongoDB 会把它判定为路径冲突，因此用户文档创建成功后，refresh token 写入失败，最终 `/auth/register` 返回 500。

修复方式：

- 使用单次 MongoDB 聚合更新管道；
- 用 `$filter` 清理过期或已消费的 token；
- 用 `$concatArrays` 原子追加新 token；
- refresh token 轮换仍通过查询条件保证旧 token 只能消费一次；
- 增加 token 添加、轮换和并发竞争回归测试。

涉及文件：

- `src/users/users.service.ts`
- `src/users/users.service.spec.ts`

提交：

```text

```

### 3.2 客户端 v3、服务端配置仍报告 v2

客户端已经使用 v3 复合游标，服务端 `/sync/changes` 也返回 `nextCursor/hasMore`，但服务端配置仍硬编码 `protocolVersion: 2`。

旧客户端逻辑在看到较低版本时可能调用 `/sync/reset`，造成不必要甚至破坏性的远端重置。

修复方式：

- 增加 `CURRENT_SYNC_PROTOCOL_VERSION = 3`；
- 新配置默认使用 v3；
- 已有 v1/v2 配置在读取时原地升级到 v3；
- 升级只修改配置版本，不删除任何云端文档；
- 服务端不会把高于当前版本的配置强制降级；
- `resetState` 和 `updateConfig` 统一写入 v3。

涉及文件：

- `src/sync/sync.service.ts`
- `src/sync/sync.service.spec.ts`

提交同样包含在 `109830e` 中。

### 3.3 登录后同步立即显示 `request_error`

现象：

```text

待处理：0
上次成功：尚未完成
失败分类：request_error
```

根因是登录后的第一轮同步会先上传设置。客户端发送以下字段：

- `previewFontSize`
- `previewLineHeight`
- `previewZoomSync`

- 在 `UpdateConfigDto` 中补齐三个字段和类型校验；
- 在 MongoDB `SyncConfig` schema 中增加对应字段；
- 在配置序列化/反序列化中保留这些字段；
- schema 的协议默认值同步改为 v3；
- 增加“真实桌面客户端设置快照通过严格 DTO 校验”的测试；

## 4. 客户端增量同步重构

以下改动位于 `C:\Code\React\mde-tauri` 当前工作区。它们尚未形成客户端提交，不能等同于已经发布。

### 4.1 协议层拆分

新增纯协议模块：

- `src/services/sync/syncTransport.js`
  - 集中封装 `/sync/config`、`/sync/changes`、`/sync/file/:id` 和 binding 请求；
  - 让同步状态机不再直接依赖 Axios 请求形状。
- `src/services/sync/changeProtocol.js`
  - 统一构造 v3 `cursor/limit` 参数；
  - 校验 `nextCursor/hasMore`；
  - 拒绝“有下一页但 cursor 不前进”的服务端响应；
  - 拉取页大小调整为 25，降低逐文件正文请求触发限流的风险。
- `src/services/sync/contentCodec.js`
  - gzip 编解码；
  - SHA-256、size 完整性校验；
  - 解压后大小上限；
  - 按完整 JSON 请求体估算上传体积。
- `src/services/sync/retryPolicy.js`
  - 区分临时错误和永久错误；
  - 支持 `Retry-After`；
  - 对 400、413、协议错误和完整性错误停止无意义重试。

### 4.2 持久 outbox 和崩溃恢复

原实现会把 mutation 持久化为 `processing`，但重启后只消费 `pending`，导致队列永久卡死。

当前重构包括：

- 启动迁移把遗留 `processing` 恢复为可重试状态；
- mutation 保留稳定 `mutationId`；
- 发送时固定使用入队时的 `baseRev`，不再用最新服务端 rev 强行“重基”；
- 同一文件的后继操作不能越过 in-flight 操作；
- 永久失败进入 `blocked/dead-letter`，不会持续重试；
- “立即重试”调用 `retryNow()`，先解锁可人工重试项再运行同步；
- 同步开关从 off 切换为 on 时自动启动正文同步；
- 并发 `fullSync()` 复用同一个 Promise，飞行中新增请求只补跑一轮。

### 4.3 checksum 和冲突语义

原实现把一个 `checksum` 字段同时当成“当前本地正文 hash”和“最后服务端确认 hash”，可能把有待推改动的文件误判为本地未修改，并丢弃 outbox。

当前重构方向：

- 拆分本地 checksum 和服务端确认 checksum；
- 冲突文件的 mutation 进入 blocked，不允许后续自动保存绕过冲突；
- 冲突记录、文档 rev 和 outbox 阻塞状态使用一次状态更新维护；
- “保留本地”通过 `replaceConflictWithMutation` 原子替换为基于远端 rev 的新操作；
- binding mutation 与正文 mutation 分开判断，避免远端正文拉取误删重命名 binding。

### 4.4 拉取完整性和 checkpoint

原实现可能在正文解码失败后仍推进 cursor，导致损坏事件被永久跳过。

当前重构包括：

- 拉取正文必须通过 gzip、size 和 SHA-256 校验；
- 解码、hash 或落盘失败时不得确认该变更；
- 小批量应用远端变更；
- 成功项可持久化，失败项不会被 checkpoint 越过；
- 对服务端返回的游标形状进行严格合同校验。

### 4.5 本地 reconciliation

纯事件队列无法覆盖以下情况：

- 同步关闭期间编辑；
- 应用在“写盘完成、入队前”崩溃；
- 历史版本清空队列；
- 外部 `cloud://` 文档编辑只写缓存但未成功入队。

当前同步周期增加本地 reconciliation，用磁盘内容、external cache、fileId 映射和已确认服务端 hash 重建遗漏的 dirty/outbox 状态。

### 4.6 账号隔离和会话切换

异步编码、持久化和网络请求期间可能发生 A 用户切换到 B 用户。原入口在 await 后读取“当前用户”，存在把 A 的正文写入 B outbox 的风险。

当前重构在同步周期和 mutation API 入口捕获账号 scope，并在关键 await 后重新断言；会话变化时终止该操作，避免跨账号污染。

### 4.7 设置同步和隐私

客户端现在把以下字段视为设备本地配置，不上传到云端：

- `workspacePath`
- `serverUrl`
- `syncEnabled`

同时增加独立的 `syncableConfigUpdatedAt`，避免仅修改设备本地字段时，用较新的总时间戳覆盖另一台设备的主题、字体等云设置。

### 4.8 文件删除和 UI 语义

原交互存在反转：

- 真正从文件树删除文件时没有生成云端墓碑；
- 取消收藏或移除“最近文件”却可能删除云端副本。

当前改动将收藏/最近列表与云端删除语义拆开，并为文件树删除增加 staged deletion：先记录可恢复的删除意图，再删除本地文件并提交云端墓碑。同步状态 UI 也改为显示账号级状态、失败分类、待处理数和可执行的立即重试。

## 7. 修复后的同步流程

```text
本地保存
  -> 持久化 dirty/outbox
  -> 捕获并校验账号 scope
  -> 拉取 v3 增量变更
  -> 校验正文 gzip/size/SHA-256
  -> 冲突则原子阻塞并等待用户裁决
  -> 无冲突则持久化应用并推进 checkpoint
  -> 按 immutable baseRev 推送 outbox
  -> 成功后更新服务端确认 hash/rev
  -> 临时错误按 Retry-After/退避重试
  -> 永久错误进入 blocked 并显示给用户
```

这里的“增量”目前指按 dirty 文档和变更游标增量传输；单个文件更新仍传输完整正文，并不是文本 diff/patch。
